# ICP-бот

Telegram-бот, который следит за Internet Computer (ICP): курс, оборот за
24 часа, соотношение покупок и продаж, и уведомление при резком росте.

Данные берутся у криптобиржи, а не у новостных лент по акциям: у тех ICP просто
нет. Проверено напрямую — на запрос по этому тикеру приходит «No share class
found for symbol», пустая история цен и ноль новостей.

## Что умеет

**`/icp`** — снимок рынка за последние 24 часа:

- цена, изменение в процентах, максимум и минимум;
- оборот в ICP и в долларах, число сделок;
- сколько покупали и сколько продавали, в монетах, деньгах и процентах.

**Уведомления о резких движениях** приходят сами на пяти уровнях: рост на +5%
и +10%, падение на -2%, -4% и -6% за 24 часа. Каждый уровень взводится
отдельно, поэтому рост через пятёрку и рост через десятку — два разных
события, а не одно повторённое; падения устроены так же. Прыжок сразу через
несколько уровней одной стороны даёт одно сообщение про самый дальний
пройденный. Уровни задаются в `alert_levels.py`.

Рост и падение никогда не срабатывают вместе: одно и то же суточное изменение
не может быть одновременно выше +5% и ниже -2%.

**`/alerts on|off`** — переключатель уведомлений для каждого пользователя
отдельно: один отключил — остальные продолжают получать.

## Откуда данные

Публичный API Binance, **без ключа и без аккаунта** — поэтому у бота нет
никаких секретов, кроме токена Telegram.

- `ticker/24hr` — цена, процент, максимум, минимум, оборот, число сделок;
- `klines` за 24 часовые свечи — из них берётся разбивка покупок и продаж.

Про разбивку важно понимать: Binance отдаёт объём по **инициатору** сделки
(тейкеру). У каждой сделки всегда есть и покупатель, и продавец, поэтому
«покупали 45%» означает «45% объёма прошло по инициативе покупателей», а не
буквальный подсчёт. Это стандартная оценка давления на цену, и в сообщении
бота она подписана именно так, чтобы не вводить в заблуждение.

Часовые свечи, а не дневная, выбраны намеренно: дневная означала бы «с 00:00
UTC» и тихо расходилась бы с процентом изменения рядом, который считается за
скользящие сутки.

## Как устроено уведомление

Сложность порогового алерта не в том, чтобы заметить порог, а в том, чтобы не
прислать его пятьдесят раз подряд. Поэтому каждый уровень — отдельный автомат
на два состояния, сохранённый в базе: он «взведён», пока не сработает, и
взводится обратно, только когда движение отступит за более близкую отметку —
ниже неё для роста, выше для падения.

У роста зазор шире: +10% взводится обратно на +8%. У падений уровни стоят
плотнее, через два пункта, поэтому и зазор один пункт: -4% взводится на -3%.
Этот зазор не даёт цене, зависшей ровно на пороге, звонить каждый цикл.

Состояние лежит в базе, а не в памяти, чтобы перезапуск не присылал заново уже
полученное уведомление. Уровни, которых в сохранённом состоянии ещё нет,
считаются взведёнными — поэтому добавление новых уровней не требует сброса.

## Запуск локально

```bash
cp .env.example .env          # вписать TELEGRAM_BOT_TOKEN
python -m venv .venv
.venv/Scripts/activate        # Windows; на Linux/macOS — source .venv/bin/activate
pip install -r requirements.txt
python main.py
```

Свой `chat_id` для `ADMIN_CHAT_IDS` можно узнать, отправив боту `/whoami`.

## Деплой на Railway

1. Создать сервис из GitHub-репозитория, тип — **worker** (входящие порты не нужны).
2. Перенести переменные из `.env` в Railway Variables. `.env` в репозиторий не
   попадает — он в `.gitignore`.
3. Подключить том и выставить `DATABASE_PATH=/data/bot.db`. **Без этого база
   стирается при каждом деплое**, а вместе с ней — состояние алерта и список
   пользователей.

## Что заложено с самого начала

- **Конфигурация падает на старте**, если нет токена, и проверяет секреты на
  ASCII: ключ с «умными» кавычками ломает вызовы глубоко внутри SDK без внятной
  ошибки.
- **Секреты вырезаются из логов** (`logging_setup.py`) — включая трейсбеки.
  `httpx` пишет полный URL каждого запроса на уровне INFO, поэтому любой API с
  ключом в query-параметре печатает этот ключ в каждую строку логов.
- **Таблица `seen`** с уникальной вставкой — дешёвая идемпотентность, если
  появится второй источник данных.
- **Админские команды не видны** обычным пользователям, но проверка прав живёт
  в самих хендлерах, а не только в меню.

И три правила, которые дёшево соблюдать сразу и дорого внедрять потом:

1. Чекпоинт фонового цикла ограничивайте окном — сохранённая метка может
   оказаться недельной давности и вывалить пользователям бэклог.
2. Логируйте сырой ответ источника хотя бы первые несколько раз за соединение.
   Иначе «источник молчит» и «источник шлёт то, что мы молча выбрасываем»
   выглядят в логах одинаково.
3. В вебсокет не пишите ничего сверх протокола: лишний текстовый кадр может
   обрубить поток данных, оставив соединение живым на вид.
